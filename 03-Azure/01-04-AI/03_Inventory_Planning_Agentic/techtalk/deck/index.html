So how much should Zava order? The hack keeps the planning rule deliberately simple, and it lives in Python, in a function tool called calc_reorder. Here are six weeks of leaf blower sales across the four stores. Twenty a week, and then the last two weeks jump to twenty-eight. [click]

Twenty-eight last week, divided by seven, is four a day. Times thirty days is a hundred and twenty. Seattle has six on the shelf. So the order is a hundred and fourteen.

And that is exactly the first line of the plan we recorded when we ran the hack: 114, then 112 for Portland, 64 and 62 chainsaws, 91 and 75 hedge trimmers.

Here's the important design choice: the model never does this arithmetic. It decides which product and which location to look at, and then it calls the function. The numbers come from your code and your data.

Part 3 / Only a person says yes

Asking nicely is not a gate

Two locks on submit_purchase_order. Only one of them is real.

replenishment-action-agent

asks to submit

Lock 1 · the prompt

"You NEVER submit an order yourself without approval."

src/agents/__init__.py, REPLENISHMENT

only a request

Lock 2 · the code

APPROVAL_REQUIRED = {"submit_purchase_order"}

if call.name in APPROVAL_REQUIRED:
    # Pause: a human must approve this action before we act.
    return ToolApprovalRequest(tool_name=call.name, arguments=args)

src/agent_runtime.py, run()

ToolApprovalRequest

returned to the console, not run

In the trace of replenishment-action-agent

get_product looked up the unit costs

submit_purchase_order not there: the code held it

approve() in orchestrator.py runs it after a yes

A prompt asks. Code decides who can write.

The call slipping past the prompt is illustrative: the code stops it either way. Trace finding from challenge 4, Part D.

[12:00, 2 minutes] I let both locks appear and read the prompt line aloud.

There are two locks on the write tool. The first is in the prompt: "You NEVER submit an order yourself without approval." That's a good instruction. But it's a sentence, and a model can ignore a sentence. The second lock is in the code: a set called APPROVAL_REQUIRED, with exactly one name in it.

So let's imagine the worst case: the model asks for submit_purchase_order anyway. [click]

(I wait while the call slips past the dashed line.) The prompt doesn't stop it. It was only ever a request. But when the call reaches the runtime, the code checks that set, and instead of running the tool it returns a ToolApprovalRequest to the console. Nothing is written.

You'll see it yourself in challenge 4: in the trace of the replenishment agent there are get_product calls, and no submit_purchase_order at all. The only thing that runs it is approve() in the orchestrator, and only a person's click calls that.

That's the line I'd like you to remember: a prompt asks; code decides who can write.

[14:00, 2 minutes] I let the pipeline build from left to right.

Planners don't want to click four buttons, and they don't watch a dashboard all day. So in the last challenge the loop starts itself. A new signal lands in the signals container in Cosmos DB. A watcher in the console app reads the Cosmos change feed every three seconds. When something new arrives, it runs sense, plan and propose with the same three agents. And then it stops, at the same gate. [click]

And it doesn't matter who writes the signal. (I let each source fire in turn.) The Inject button in the console. An MCP client, so GitHub Copilot or another agent, calling a tool called inject_signal. Or anything else that can write a document: Data Explorer, a script, a scheduled job.

The design choice that makes this clean: the signal endpoint never calls an agent. It only writes. The change feed is the only trigger, so every writer gets exactly the same reaction, and it always ends at the gate.
