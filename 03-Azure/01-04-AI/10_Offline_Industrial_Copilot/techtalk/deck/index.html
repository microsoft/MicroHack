So the technician asks the obvious question: at what vibration level must this spindle be stopped? Normally that question goes from the tablet, through the plant network, through the firewall, out to the internet and up to a big model in the cloud.

And on a factory floor, that last link is the weak one. That's the whole idea of today: the answer has to live next to the machine.

[3:20, 2 minutes 30] I talk the room through the build as it happens: the boundary, Foundry Local, the agent, then the four tools one at a time.

Here is what you build. Everything inside this dashed line is one laptop, or a small VM. Nothing inside it needs the internet.

At the bottom is Foundry Local. It downloads models once, runs them on your GPU, NPU or CPU, and gives you an OpenAI-compatible endpoint on localhost. So your code uses the normal OpenAI SDK; only the base URL changes.

On top of that sits the agent: a small language model, phi-4-mini, with function calling. It has four tools. Machine status reads a local JSON file. Maintenance tickets writes to a local file, and notice the badge: anything that changes something waits for a person to say yes. SOP search finds the right procedure with a local embedding model. And a fault classifier predicts what is about to break.

[click] That classifier is the one piece that comes from the cloud. You train it in Azure Machine Learning, export it to ONNX, and copy it onto the device. (I wait for the file to land.) Then the cloud is not needed at run time. That's the pattern for the whole day: use the cloud to build, and the device to run.

In challenge 2, teams run a benchmark on three small models. These are our numbers, on a Snapdragon laptop. Look at speed first. qwen3 is the quickest at 27 tokens per second, phi-4-mini does 21, and the NPU build of qwen2.5 does 4, and it took 47 seconds just to load. If you stopped here, you'd pick qwen3.

[click] But an agent has to call tools. So we give each model 8 requests that need a tool and force a tool call. phi-4-mini gets 7 of 8 right. qwen3 gets 1. And the NPU build of qwen2.5 doesn't answer at all: on this Foundry Local version, any request that includes tools returns an HTTP 500. That is exactly the kind of thing you only find by trying.

[click] Last, answer quality on 13 questions from the procedures. phi-4-mini and qwen2.5 get all 13, qwen3 gets 9. So the fastest model is not the one that can use the tools. We pick phi-4-mini on the GPU, and the rest of the day runs on it.

Your numbers will differ, because they depend on the hardware and the model version. That's the point: measure on the device you'll deploy to. And if time is short, every script has a quick mode.

Here's a surprise from challenge 3. Each dot is one request a technician might type, grouped by the tool that should answer it. With all four tools in front of it, phi-4-mini gets 19 of 23 right on this run. In other runs it was as low as 14.

And look at the four misses. "Run a diagnosis on CNC-07." "Classify the condition of PRESS-02." Two ticket requests. Every single one went to machine status. The model sees a machine name and grabs the status tool.

[click] The fix is a router, and it costs almost nothing. Before the model sees a request, we compare it with a short card for each tool, using the embedding model we already loaded for search. Then we show the model only the best match. (I let the scan pass and the red dots flip.) 23 of 23.

And look at the time: 230 seconds for the set instead of 778. Fewer tools in the prompt means less work for a small model. That's a lesson that applies far beyond the factory: on small models, give the model fewer choices.

This is challenge 6, and it is my favourite moment of the day. On the left is everything the copilot can do. On the right is the internet: Foundry Local's catalog lives in eight Azure regions. Right now, everything is connected and everything is green.

Now, let's pull the cable. [click]

(I stay quiet while the plug comes out and the regions fail one by one.) That error is real, we recorded it: Foundry Local tried all eight regions and got a transport failure every time. So the internet is truly gone.

And now the copilot checks each capability again. The local model answers. Machine status. The fault prediction. The SOP answer with its sources. A ticket, after the technician approves it. Every lamp turns green again. All of it came from the device.

One more test, because this is where people get caught. [click] What if the service restarts while you're offline? A power cut, an update. (I let the device go dark and come back.) On Foundry Local 0.14, the models load from the local cache, phi-4-mini in about 5 seconds, the embedding model in about 3, and the whole copilot answers again. Everything still answers.

A tip for the room: on a managed laptop, a firewall rule for "Internet" did not block Foundry Local for us. We had to block the programs themselves. The walkthrough has the exact rules. Test it, don't assume it.
